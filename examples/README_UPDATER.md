# Auto-updater prototype

> ⚠️ **DEMO / NOT FOR PRODUCTION** — This is a local-testing prototype that
> demonstrates signed-manifest update mechanics. Read the
> [Production hardening](#production-hardening) section before considering any
> real deployment.

This directory contains a self-contained auto-updater prototype for the
jitterbugs project.

## Files

| File | Purpose |
|------|---------|
| `updater.py` | Python updater client (this prototype) |
| `manifest_example.json` | Sample update manifest for local testing |
| `.version` | Local version file read by the updater |
| `server.py` | TLS development server (see `examples/server.py`) |

## How it works

```
┌─────────────────────────────────────────────────────────┐
│ 1. Fetch manifest.json  (HTTPS)                         │
│ 2. Fetch manifest.json.sig  (HTTPS)                     │
│ 3. Verify RSA-PKCS1v15/SHA-256 signature                │
│ 4. Compare remote version > local version file          │
│ 5. Download artifact  (HTTPS)                           │
│ 6. Verify SHA-256 checksum                              │
│ 7. Write to temp dir → atomic swap into examples/current│
│ 8. Keep backup of previous install for rollback         │
│ 9. Log every step to examples/updater.log               │
└─────────────────────────────────────────────────────────┘
```

## Quick-start (local testing)

### 1 — Install Python dependencies

```bash
pip install -r requirements.txt
# requires: requests>=2.28, cryptography>=3.4
```

### 2 — Generate a signing keypair

```bash
bash scripts/make-update-keys.sh
```

This writes three files into `examples/`:

| File | Description |
|------|-------------|
| `update_signing_key.pem` | RSA 4096-bit private key (**never commit this**) |
| `update_public_key.pem`  | Corresponding public key |
| `manifest_example.json.sig` | Binary detached signature of the manifest |
| `manifest_example.json.sig.b64` | Base-64 encoded signature |

> The private key is `chmod 600` and is listed in `.gitignore`.
> Never commit it to version control.

### 3 — Host the manifest and artifact via the TLS server

The development TLS server is at `examples/server.py`. Start it (requires the
test certificates generated by `scripts/make-certs.sh`):

```bash
# Generate TLS certs for the local server first (if not done already)
bash scripts/make-certs.sh

# Start the TLS server
python examples/server.py
# Listening on https://localhost:8443
```

The server serves files from the `examples/` directory under the `/updates/`
path prefix.  Copy (or symlink) your manifest and artifact there:

```bash
cp examples/manifest_example.json examples/manifest.json
cp examples/manifest_example.json.sig examples/manifest.json.sig
# Add a dummy artifact to test the full flow
echo "demo artifact" | gzip > examples/jitterbugs-2026.03.19.tar.gz
```

### 4 — Run the updater in check-only mode

```bash
python examples/updater.py \
  --manifest-url https://localhost:8443/updates/manifest.json \
  --sig-url      https://localhost:8443/updates/manifest.json.sig \
  --public-key-file examples/update_public_key.pem \
  --no-verify-tls \
  --check-only
```

`--no-verify-tls` is needed because the development server uses a self-signed
certificate.  In production, **always** use a CA-trusted certificate and
remove this flag.

### 5 — Run the updater in auto mode (installs without prompting)

```bash
python examples/updater.py \
  --manifest-url https://localhost:8443/updates/manifest.json \
  --sig-url      https://localhost:8443/updates/manifest.json.sig \
  --public-key-file examples/update_public_key.pem \
  --no-verify-tls \
  --auto
```

After a successful install, `examples/current/` contains the downloaded
artifact and `examples/backup/` holds the previous version for rollback.
`examples/.version` is updated to the new version string.

### 6 — Verify an existing installation

```bash
python examples/updater.py \
  --manifest-url https://localhost:8443/updates/manifest.json \
  --sig-url      https://localhost:8443/updates/manifest.json.sig \
  --public-key-file examples/update_public_key.pem \
  --no-verify-tls \
  --verify
```

## CLI reference

| Flag | Default | Description |
|------|---------|-------------|
| `--check-only` | off | Report available update without installing |
| `--auto` | off | Install without interactive prompt |
| `--manifest-url URL` | `https://localhost:8443/updates/manifest.json` | Manifest URL |
| `--sig-url URL` | `https://localhost:8443/updates/manifest.json.sig` | Detached sig URL |
| `--verify` | off | Verify current install integrity and exit |
| `--version-file PATH` | `examples/.version` | Local version file |
| `--public-key-file PATH` | embedded demo key | PEM public key override |
| `--no-verify-tls` | off | Disable TLS cert verification (**INSECURE**) |

## Production hardening

The following measures are **required** before using anything derived from this
prototype in a real product.

### Certificate management (ACME / Let's Encrypt)

- Obtain server certificates from a public CA via the ACME protocol
  (e.g. [Certbot](https://certbot.eff.org/) or
  [acme.sh](https://github.com/acmesh-official/acme.sh)).
- Automate renewal so certs never expire.
- Remove `--no-verify-tls`; let the OS/platform trust store validate the cert.

### Private key protection (HSM / secure enclave)

- Store the signing private key in a Hardware Security Module (HSM),
  cloud KMS (AWS KMS, GCP Cloud KMS, Azure Key Vault), or OS key store.
- The key should **never** exist as a plaintext PEM file in production.
- Use PKCS#11 or provider-specific APIs to perform signing without
  extracting the key material.

### Mutual TLS (mTLS) for strong device identity

- Issue client certificates to each device via an internal CA.
- Store client private keys in the device TPM or secure element.
- Configure the update server to require and verify client certificates
  (`ssl.CERT_REQUIRED` + `load_verify_locations`).

### Key rotation

- Rotate signing keys on a regular schedule (e.g. annually, or on
  compromise).
- Publish the new public key via a signed key-rotation manifest so
  existing clients can trust the new key.
- Keep the old key valid during a transition window to avoid breaking
  clients that haven't updated yet.

### Polling cadence and user consent

- **Do not** poll more frequently than your release cadence justifies.
  Hourly or daily is appropriate for most software; 20-second intervals
  cause unnecessary load and are not recommended except in tightly
  controlled environments.
- Add random jitter (e.g. ± 10 %) to spread client load across time.
- Use HTTP conditional GETs (`If-Modified-Since` / `ETag`) so the server
  can respond `304 Not Modified` cheaply when nothing has changed.
- Obtain **explicit user consent** for automatic installation; provide a
  clear opt-out mechanism.

### Additional recommendations

| Area | Recommendation |
|------|---------------|
| Artifact signing | Sign artifacts (not just manifests) to bind the binary to the manifest |
| Checksum storage | Store expected checksums locally to avoid re-downloading for `--verify` |
| Rollback policy | Define a maximum number of rollback steps; alert on repeated failures |
| Audit logging | Write update events to a tamper-evident log (append-only, off-device) |
| Network hardening | Use HSTS, DNS-over-TLS, and content delivery networks for distribution |
| Dependency scanning | Regularly scan `requests` and `cryptography` for known CVEs |

## Security notes

- The **embedded public key** in `examples/updater.py` is a placeholder that
  will **always fail** signature verification. You must replace it with your
  real public key (or pass `--public-key-file`) before running any meaningful
  test.
- The `update_signing_key.pem` private key generated by
  `scripts/make-update-keys.sh` is listed in `.gitignore`. If you accidentally
  commit it, rotate the key immediately and consider all signatures made with
  it compromised.
- This prototype does not implement certificate pinning, OCSP checking,
  or HSTS. These are not necessary for a local demo but are recommended for
  production.
